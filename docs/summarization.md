# 长对话总结：一次总结多少 token 合适

这篇回答三个问题：**累计多少 token 触发一次总结**、**能不能按模糊 token 估计**，
以及最容易被忽略的那个 —— **总结完之后，摘要怎么回到 prompt 里**（第 5 节）。
配套行为还有：**总结完成后隐藏被覆盖的正文**。

所有阈值都在 `server/src/domain/constants.js` 的 `SUMMARY_POLICY` 里定义一次，
由 `GET /api/meta` 下发给前端（面板里的同名字段填 `0`/`-1` 即"用服务端建议值"）。
所以调参改一处，前后端同时生效。

---

## 1. 结论

| 项 | 默认值 | 含义 |
|---|---|---|
| `triggerTokens` | **6000** | 未总结区间的累计估算 token 达到该值 → 触发一次总结 |
| `minTokens` | 1500 | 低于此值不触发（碎片摘要信息密度太低） |
| `maxBatchTokens` | 12000 | 单批总结的输入上限，超出的部分留到下一批 |
| `maxSummaryChars` | 800 | 摘要正文长度上限（字符），超长由后端截断 |
| `keepRecentMessages` | 6 | 总结后保留最近 N 条**不隐藏**；`0` = 被总结的正文全部隐藏 |
| `limits` | 1000–20000 | 面板输入框的合法区间 |

按模型上下文规模的选择建议（`summaryPolicy.presets`，面板原样展示）：

| 模型上下文 | 建议 `triggerTokens` | 理由 |
|---|---|---|
| 8192 | 3000 | 固定开销（系统提示 + 角色卡）占比大，宁小勿大 |
| 16384 | **6000** | 默认量级，粒度与安全兼顾 |
| 32768 | 10000 | 可按"一场戏"为单位总结 |
| 131072 | 12000 | 不建议再加：再长摘要本身就失焦了 |

---

## 2. 模糊 token 估计：可以，而且口径必须与后端同源

真实分词需要模型自带的 tokenizer，前端不可能持有。所以采用**字符数换算**：

```
估算 token ≈ ⌈字符数 / charsPerToken⌉        // 默认 charsPerToken = 2
```

- 这是**中英混合的保守估算**，不是真实分词。
- `charsPerToken` 由服务端下发（`scoring.tokenEstimation.charsPerToken`），**前端不写死这个 2**；
  公式文本 `formula` 里的数字也由同一个常量生成，不会出现"文案说 2、参数是 3"的分裂。
- 为什么必须同源：前端用它算"还剩多少才触发"，后端用它算"注入预算放不放得下"。
  两边系数不一致，就会出现"前端以为还早、后端已经爆预算"。
- 契约未载入、或服务端没给系数时，前端**不做估算**，整个总结功能标记为不可用并说明原因 ——
  而不是拿 2 兜底（那等于在前端藏了一份语义）。

估算的输入是**未总结区间内、且未被隐藏的全部正文**，每次检查现算：

```
累计 token = ⌈(楼层 [summarizedUpTo+1 .. 最后一条] 内可见消息的字符总数) / charsPerToken⌉
```

**为什么现算而不是增量累加**：用户随时可能编辑、删除、撤销隐藏楼层。增量计数会漂移；
按区间实算天然免疫，代价只是一次线性遍历（几十条消息的字符串长度求和）。

## 3. 为什么默认 6000

三个约束同时成立才是一个好阈值：

**① 单次总结的输入不能撑爆上下文**
总结要把累积的原文整个喂给 LLM。阈值 ≈ 单次输入规模。以 16k 上下文为默认目标：

```
6000 (待总结原文) + 2000~4000 (系统提示 + 角色卡 + 人设) + ~800 (输出摘要) ≈ 10k  → 余量充足
```

8k 上下文的模型按同式会到 9k 左右，所以预设把它的建议值下调到 3000。

**② 粒度要落在"场"上，而不是"句"上**
按本系统的估算口径，典型中文角色扮演：

- 单条角色回复 300–600 字 → 约 150–300 token
- 一轮往返（用户 + 角色）→ 约 300–600 token
- 6000 token ≈ **20 条消息 / 10 轮往返** ≈ 一小场戏

一场戏总结一次，摘要之间有清晰的叙事边界；再密就变成"流水账摘要"，再疏就跨场混淆。

**③ 摘要不能挤垮注入预算**
注入侧 `tokenBudget` 默认 1200。若每 1500 token 就总结一次，一次长会话会攒出几十条摘要，
彼此在注入预算里互相挤。6000 的节奏下，一场 3 小时、约 60k token 的会话大约产生 10 条摘要，量级合适。

> 旁证：社区经验里"8192 上下文约能总结 15–20 条消息"与本系统 6000 token（约 20 条）基本吻合。

**下限 1500 的理由**：低于这个量总结出来的内容往往只是"刚才发生了什么"，
信息密度还不如直接留在上下文里，白占一次 LLM 调用和一条注入位。

## 4. 触发之后：隐藏被覆盖的正文

总结完，原文就该从 prompt 里退场 —— 否则等于同一段信息付了两遍 token。
本项目用**酒馆原生的隐藏机制**，不自己造一套。

### 4.1 机制

酒馆的 `/hide` / `/unhide <楼层或区间>` 本质是对消息置 `chat[i].is_system`：

- `is_system === true` 的消息**不进入 prompt**；
- 它们在 UI 上仍可见（带 ghost 标记），**不删除、可随时 `/unhide` 放回**。

隐藏是**可逆**的，这是选它的理由：删除不可逆，而总结可能出错。

顺带一个天然的一致性：本扩展收集对话原文时本来就跳过 `is_system` 的消息。
所以隐藏之后，这些正文**既不会进 prompt，也不会再被抽取或计入累计 token** ——
不需要额外写排除逻辑，两端自动对齐。

前端实现上**优先调用酒馆命令**（它自己会刷新 UI 上的 ghost 标记），
拿不到命令执行器时退回直接置位并尽力通知 UI 刷新。失败只记日志，不影响对话。

### 4.2 两个边界：为什么不是简单地"隐藏全部"

只用一个"已处理到哪"的游标是不够的，会掉进两个坑：要么重复总结同一段，要么把最近几轮也一起隐藏、
让模型完全失去逐字近因。所以状态里记两个边界（存在 `chat_metadata`，随 chat 文件走）：

| 字段 | 含义 | 作用 |
|---|---|---|
| `summarizedUpTo` | 已被**总结**覆盖到的楼层 | 决定累计 token 从哪算起 —— 已进摘要的不再重复总结 |
| `hiddenUpTo` | 已被**隐藏**到哪一层 | 决定下次从哪继续隐藏；这些楼层不进 prompt，也不计入累计 |

两者之差，就是"**已总结、但仍逐字保留在上下文里**"的那几条。

走一遍（`keepRecentMessages = 6`）：

```
初始          summarizedUpTo=-1   hiddenUpTo=-1
消息 0..29 累计 ≥ 6000
  → 总结 0..29，summarizedUpTo=29
  → 隐藏 [0, 29-6=23]，hiddenUpTo=23      保留 24..29 逐字可见
消息 30..49 再次累计 ≥ 6000
  → 总结 30..49，summarizedUpTo=49
  → 隐藏 [24, 49-6=43]，hiddenUpTo=43     上批保留的 24..29 此时一并隐藏
```

`keepRecentMessages = 0` 时 `hiddenUpTo` 与 `summarizedUpTo` 重合，**被总结的正文全部隐藏** ——
这就是"总结一次、正文全隐"的配置。代价是模型只能靠摘要和检索注入了解这段时间，
容易出现细节遗忘或口吻漂移，所以默认给 6，把选择权留给面板上的一个数字。

### 4.3 楼层被编辑过怎么办

总结记录用的是楼层号，用户删楼会让它错位。所以每次运行前做一次归一化：
若记录越界（`summarizedUpTo`/`hiddenUpTo` 大于当前最后一层），
判定为聊天被编辑过，**重置两个边界并记一条警告**，避免对错位的楼层动手。

### 4.4 面板上的三个操作

| 按钮 | 行为 |
|---|---|
| 立即总结 | 不受阈值限制，立刻总结当前待总结区间（仍受 `maxBatchTokens` 限制） |
| 取消隐藏 | 把已隐藏的正文全部放回 prompt；**不动 `summarizedUpTo`**，所以不会因此重复总结 |
| 重置总结边界 | 清空本聊天的边界记录（不删除已写入的摘要记忆，也不改变隐藏状态） |

---

### 4.5 单批上限：边界必须落在"真正被总结过"的楼层上

总结的输入本身也不能撑爆上下文，所以有 `maxBatchTokens`：一次只喂进去这么多原文，**超出部分留到下一批**。

这里有个容易写错的地方，值得单说：单批被截断时，**覆盖边界必须停在最后一个真正进了摘要的楼层**，而不是停在整个区间的末端。

```
待总结区间 0..49，但 maxBatchTokens 只装得下 0..29
  正确: summarizedUpTo = 29，隐藏 [0, 29-keep]
  错误: summarizedUpTo = 49，隐藏 [0, 49-keep]
        → 楼层 30..49 没进摘要，却被隐藏移出了 prompt
        → 它们既不在摘要里、也不在上下文里 —— 等于永久丢失
```

所以前端收集文本用的是**严格前缀**（装不下就停，不跳过它去装更靠后的消息），并在提交时把 `lastIncluded` 作为覆盖边界上报。该批是否被截断也会记在 `report.batchTruncated` 里，面板上能看到"本批只覆盖到第 N 层，余下留待下批"。

## 5. 总结之后：摘要怎么回到 prompt（【前情提要】）

这一节回答一个容易被忽略的问题：**摘要本身也是要发给 AI 的东西**。

prompt 里同时装着四样东西：角色卡（酒馆）＋ 注入的记忆 ＋ 摘要 ＋ 最近的对话原文。所以"总结"不是终点 —— 摘要**怎样回到上下文里**，才是决定它有没有用的那一步。

### 5.1 为什么摘要不能走相似度检索

摘要覆盖的正文已经被 `/hide` 移出了 prompt。也就是说：

> **对于那段剧情，摘要是唯一的载体。**

如果摘要仍按普通记忆那样参与 FTS 相似度召回，就会变成：

```
当前轮的关键词不命中某条摘要
  → 该摘要进不了 top-k
    → 它覆盖的那段剧情，在模型眼里彻底空白
```

而且这不是"偶尔漏"，是**结构性偏向漏**：摘要又长、关键词又稀，在 bm25 里天然吃亏，而相关性恰好占检索打分权重的 0.6。等于系统性地倾向于丢掉最该留下的东西。

### 5.2 做法：独立段落、按楼层顺序、必然在场

摘要被**排除出相似度召回**，改为拼成一条独立段落：

```
【前情提要】
[24-35] 与艾拉在酒馆初见后结伴出城，她自认得见过北境哨塔的金纹令…
[36-47] 哨塔哨兵拒绝放行，艾拉独自夜探，回来时袖口有血迹，未解释来历…
[48-59] 主角替她遮掩，两人关系转近；她提到"上面的人"在等她回信…
```

- **按楼层顺序**拼接，最早在前 —— 模型读到的是一条连贯的叙事链，而不是按打分排序的散点。
- **行首 `[起-止]`** 是该摘要覆盖的楼层区间，让模型知道这段剧情发生在多早之前。格式由 `meta.digestFormat` 下发，服务端组装、前端只展示。
- **只取本聊天**的摘要（`scope='chat'` 且 `chat_id` 匹配），不跨聊天拼链。
- **必然在场**：归入常驻段，不参与打分，也不会被挤掉。

于是注入文本的固定结构变成：

| # | 段 | 性质 | 回答的问题 |
|---|---|---|---|
| 1 | 角色画像 | 常驻 | 角色是谁 |
| 2 | **前情提要** | 常驻 | 到现在为止发生了什么 |
| 3 | 相关记忆 | 按需（FTS，已排除摘要） | 与当前这轮相关的旧事 |
| 4 | 相关细节 | 按需（向量） | 性格/外貌/氛围之类的细粒度印象 |

第 3 段**排除摘要**是刻意的：摘要已经在第 2 段了，再让它参与召回，只会在两处重复占位、白花一份 token。

### 5.3 预算不够时：保新丢旧

【前情提要】有**自己独立的预算**（`summaryPolicy.digest.maxTokens`，默认 2000；面板"前情提要预算"可覆盖，0 = 用服务端默认）。

为什么不和 `tokenBudget` 共用一个预算：共用就意味着摘要要和"当前轮更像"的记忆抢位子，抢不过就被挤掉 —— 而它一被挤掉，那段剧情就没了。独立预算保证它**至少不会因为"不够相关"而消失**。

预算装不下全部摘要时，**从最早的开始丢**，优先保新：

```
与可见窗口相接的最近摘要最关键 —— 它决定"刚才发生了什么"。
早期剧情里的稳定设定通常已经沉淀到角色画像与 fact 记忆里，
丢掉最早一条摘要，并不等于那些设定也消失了。
```

特殊约定：**只要有摘要，就至少保留最新一条**。所以不会出现"有摘要但前情提要为空白"的情况，也不会因为预算填得极小就整段消失。

按默认量级（`maxSummaryChars=800`、`triggerTokens=6000`），2000 token 大约容纳 **5 条摘要**，覆盖约 **150 层原文**。超出后会看到 `digestTruncated: true` 与 `digestDropped`（丢了几条）。

### 5.4 覆盖率为什么是"不重不漏"

总结只有一个方向：`summarizedUpTo` 只向前推进，永不回退。配合"覆盖楼层集合相同即复用"的去重规则，可以推出：

> 每一层楼，**最多**属于一条摘要；而只要它被总结过，就**恰好**属于一条。

- 不会重复：边界单向推进 + 集合去重，同一层不会被总结两次。
- 不会遗漏：正文被隐藏的前提是被总结（`summarizedUpTo` 先推进，隐藏才跟着推进），所以被隐藏的每一层都必然有摘要覆盖它。

这也是【前情提要】能放心做常驻段的前提 —— 它不会和"隐藏"之间出现缝隙。

### 5.5 面板上能看到什么

| 位置 | 显示 |
|---|---|
| 「记忆注入」模块 | `前情提要预算` 输入框（占位显示服务端默认值） |
| 「诊断与契约」的最近状态 | 本轮的 `前情提要 n/m 条（约 x token，独立预算 y）`，被丢弃时提示"已丢掉最早 N 条" |
| 「检索预览」 | 把**实际会注入的**【前情提要】段落原文整段显示出来，并注明"常驻·不参与打分" |

检索预览里那一整段，就是模型真正会读到的东西 —— 想确认"被隐藏的剧情还在不在"，看这里最快。

---

## 6. 去重与幂等

- 同一聊天内，**覆盖楼层集合完全相同**的摘要会被复用（`deduped: true`），不会重复入库 ——
  手工连点"立即总结"，或同一区间被重试，都不会攒出重复摘要。
- 楼层集合变了（比如多了一条）才另起一条。
- 总结**失败**时 `summarizedUpTo` 不推进，下一轮会重试同一区间。
- 总结成功后**先推进边界再隐藏**：即便隐藏失败，也不会让同一段被反复总结。

---

## 7. 调参速查

| 现象 | 调整 |
|---|---|
| 摘要太碎、一条摘要没几句话 | 调大 `triggerTokens`（如 6000 → 10000） |
| 模型经常忘了刚发生的事 | 调大 `keepRecentMessages`（6 → 8~10），或先确认"总结后隐藏"是否开得太激进 |
| 感觉模型跟不上剧情 | 调小 `triggerTokens`，让摘要更贴当前；同时检查注入 `tokenBudget` 是否够放下多条摘要 |
| LLM 报上下文超限 | 调小 `triggerTokens` 或 `maxBatchTokens`（后者决定单批喂进去多少） |
| 不希望动我的聊天记录 | 关掉"总结后隐藏被覆盖的正文" —— 总结照常写入，只是不隐藏 |
| 摘要太长、占注入额度 | 调小 `maxSummaryChars` |
| 模型对早期剧情毫无印象 | 调大"前情提要预算"（`digest.maxTokens`），让更多摘要留在常驻段 |
| 注入总长度太长、挤占对话空间 | 调小"前情提要预算"或 `maxSummaryChars`；注意它和检索 `tokenBudget` 是**两个**预算 |
| 想知道某段剧情到底还在不在 | 面板「检索预览」→ 看【前情提要】整段；这里显示的就是模型真正读到的东西 |
